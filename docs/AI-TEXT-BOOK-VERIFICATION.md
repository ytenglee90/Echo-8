## 回归中出现的失败与处理

1. 最初完整 Chromium 托管回归 210 项：206 通过、4 失败。新格式的失败用例暴露了书库未显示异步文件错误，以及测试在启动种子节点出现前计数的问题；补齐文件状态订阅，并改为先打开已知文档后验证失败保护。另三项为账户策略、重新授权和书库切换的超时/可见性失败。包含这四项的 6 项定向重跑全部通过，随后新功能最终 2 项再次通过；没有声称同一次完整回归 210 项全部通过。
2. 最初并行浏览器任务共用了默认结果目录，性能用例收尾丢失 trace 文件。后续改用独立输出目录重跑，性能回归通过。
3. WebKit 新用例初次精确匹配未选中 aria 名称，重开后节点名称带“已选中”前缀；更正语义定位。多步骤流程初始 30 秒预算不足，隔离关闭/重开页面并设 60 秒后，新功能便携及托管测试都通过。

## 尚未通过的兼容检查

- Firefox：托管和便携运行器在 `browserContext.newPage` 阶段报 `Cannot read properties of undefined (reading '_page')`，未进入画布；属于本次浏览器运行环境故障，不能宣称 Firefox 通过，也不能据此判定新书籍解析失败。Corepack 形式的浏览器安装命令还遇到 `ms-playwright/__dirlock` 权限问题；直接 Node CLI 安装检查返回成功，已存在的 Chromium/WebKit 可运行。
- WebKit 的既有完整便携启动测试仍在品牌图标 `mask-image` CSS 断言上失败（读到空值）。未改图标实现，也未把这个未通过项隐藏。新书籍功能独立的 2 项完整流程已通过，但不把它描述为 WebKit 全量兼容通过。

上述结果是本机代码和浏览器验证，不等于已经验证所有外部 AI 平台都会严格遵循输出规则。不能附文件的平台只能输出成品文本供用户保存为 TXT；这条路径也不需要本地执行脚本。
